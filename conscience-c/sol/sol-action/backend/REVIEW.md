# Correction locale candidate : refus contrôlé retrouvable

Le défaut vient du catch externe de `sol_action.dispatch` : son exception annule intention, résultat et événements du bloc, puis renvoie un refus connu. Si cette réponse réseau est perdue, la lecture actuelle ne trouve rien et le pending reste conservé. Une absence de reçu reste UNKNOWN ; elle ne prouve jamais un refus.

La candidate change uniquement `sol_action_bridge`. `execute` reçoit exactement `{core_action,core_input}`, avec action bornée à create, verify, complete ou reconcile. Le noyau existant reste appelé pour le travail. Pour un job déjà créé et une capacité autorisée, un refus P0001 appartenant à la liste explicitement contrôlée, corrélé exactement à l'action, au job et à l'UUID, avec rollback attesté par le code épinglé, peut être conservé hors du bloc annulé. Une erreur de transport, une exception inconnue ou l'absence d'issue ne crée pas de refus terminal.

`refusals` conserve la réponse connue, le hash de l'entrée sans capacités brutes, le hash de capacité, une empreinte liée aux deux identifiants et à l'action, les versions et la date. `recovery_outcomes` conserve un rapprochement de ce refus sans rappeler l'action ni l'oracle. Chaque table est append-only sous RLS sans policy, sans droits directs client. Le propriétaire SQL reste de confiance : cette conservation n'est pas WORM et n'atteste aucune identité humaine. L'acteur est seulement le détenteur de la capacité du job.

Le marqueur `effect_scope:CONTROLLED_CORE_DISPATCH_SUBTRANSACTION_ONLY` porte seulement sur le bloc SOL-Action annulé. `core_effect_scope` conserve le texte du marqueur original ; `business_effect:NONE_CORE_ACTION_ROLLED_BACK` distingue ce constat de `receipt_recording_effect:APPEND_ONLY_BRIDGE_RECEIPT_RECORDED`, qui décrit l'archivage réel. Un reçu historique décrit cet archivage d'origine, sans annoncer une nouvelle écriture lors de sa lecture.

`lookup_receipt` retrouve d'abord l'issue existante dans le noyau, puis les nouveaux reçus. Toute collision entre ces histoires est refusée. Les réponses restent historiques, les capacités/CSV sont retirés récursivement et les anciennes permissions de réemploi sont désactivées. Aucune observation PASS ou fraîcheur n'est créée par une lecture ou un rapprochement de refus.

Le nouvel `execute` et le chemin `bind` refusent de réutiliser un UUID réservé dans les tables de reprise. Leurs verrous sont coopératifs. L'ancienne RPC publique du noyau reste accessible et ignore ces tables : elle ne reçoit aucune garantie nouvelle. Une tentative ultérieure par cet ancien chemin peut créer une collision ; le lookup la refuse, il ne choisit pas arbitrairement une histoire. Le refus d'une création sans job autorisé préexistant n'est pas conservé par cette version. Les refus de la production composite bind/worker/result restent hors de cette correction.

La migration change l'empreinte du bridge. Les anciennes releases sont conservées et ne sont pas réépinglées : toute nouvelle production exige l'admission explicite d'une nouvelle release après vérification du nouveau code. Les hashes du noyau SOL-Action, d'Atelier et de Preuve ne doivent pas changer. `migration.sql` refuse un prédécesseur autre que celui relu ; elle n'est pas automatiquement rejouable. Toute issue ambiguë doit être examinée.

`tests.sql` est une variante avec helpers temporaires et rollback extérieur. `tests-no-ddl.sql` évite toute création de table/fonction : un sous-bloc annule les fixtures, conserve les observations dans une variable locale, puis vérifie les compteurs après annulation. Son contrôle TRUNCATE inspecte le trigger sans exécuter cette instruction. Aucun essai local n'a encore été exécuté par l'auteur de la candidate ; un nom de scénario et le présent fichier ne sont pas une preuve de réussite. Les tests ne lancent aucun worker ni appel HTTP et utilisent seulement des fixtures synthétiques.

`rollback.sql` restaure uniquement la fonction bridge antérieure et retire les trois helpers nouveaux, après comparaison explicite avec le runtime candidate revu. Il conserve les nouvelles tables privées et tous leurs reçus. L'ancien runtime ne consulte plus ces reçus ; ils restent lisibles par l'opérateur SQL. Le déploiement applicatif doit être rétabli avec lui. Aucun retrait ou déploiement distant n'est exécuté par ces fichiers.
